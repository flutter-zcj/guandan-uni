# 联机对战与微信邀请：技术方案评估

> 结论先说：**房间号联机必须上服务端，推荐先用 Node.js 方案（2-3 天可玩），ET 留着做长期平台**。
> **微信邀请的真实卡点是域名备案 + 证书**，不是代码。

| 项目 | 现状 |
|---|---|

| 规则引擎 | `src/game/engine/*`（card/rule/hint/table/ai）纯 JS，无 DOM 依赖 |

关键点：**规则引擎是纯 JS 且不依赖浏览器**，可以直接被 Node 服务端 `import` 复用，零重写成本。

## 二、微信邀请：三条路径的真实门槛

| 路径 | 用户看到的效果 | 需要什么 | 可行性 |
|---|---|---|---|
| **A. H5 链接分享**（推荐先做） | 微信群里发一条链接，点开进房间 | ① 已备案域名 ② 该域名的有效 HTTPS 证书 | ⭐⭐⭐⭐ 最快 |
| **B. 公众号自定义分享卡片** | 分享出去是带标题、图标的卡片，而不是光秃秃的链接 | A 的全部 + 已认证**服务号** + JS 接口安全域名配置 + 后端提供 `jsapi_ticket` 签名接口 | ⭐⭐⭐ 中等 |
| **C. 微信小游戏** | 微信内搜到、可分享、可邀请 | 企业主体 + 游戏类目 + **棋牌类需游戏版号** | ⭐ 门槛极高 |

### 当前部署为什么在微信里打不开

- 现在是 **IP 地址 + 自签证书**：微信内置浏览器对自签证书直接拦截（提示证书不受信任 / 白屏）
- 即使忽略证书，IP 也无法配置 JS-SDK 的安全域名
- **必须先有备案域名**（服务器在国内，域名未备案无法解析到境内主机）

> 所以「微信邀请」这件事：**代码半天能写完，域名备案要 3-20 个工作日**。这是唯一的长周期项。

### 不受域名限制的替代做法

- 微信里直接发文字链接（`https://域名/guandan/?room=1234`），点开进房 —— 只要域名 + 证书就够，**不需要公众号**
- 群里发「房间号 1234，进来打牌」+ 游戏内「复制邀请链接」按钮
- 这些都能在 A 路径内完成

## 三、房间号联机：需要补什么

单机版是「客户端自己算」，联机版必须改成「服务端权威」：

```
玩家A ──┐
玩家B ──┼─ WebSocket ─→ 房间服务（权威牌局） ─→ 广播状态
玩家C ──┤                  ├ 房间创建/加入（6位房间号）
玩家D ──┘                  ├ 座位分配 + 掉线托管
                           ├ 服务端洗牌发牌（防作弊）
                           ├ 出牌合法性校验（复用 Rule）
                           └ 断线重连 / 超时自动过牌
```

### 必须实现的服务端能力

| 模块 | 说明 | 工作量 |
|---|---|---|
| 房间管理 | 创建/加入/离开、6 位房间号、密码可选 | 0.5 天 |
| 座位与准备 | 4 座、空位机器人补位、准备/开始 | 0.5 天 |
| 权威牌局 | 服务端 `GameTable` 驱动，客户端只做渲染 | 1 天 |
| 协议与广播 | 出牌/过牌/结算/状态同步 | 1 天 |
| 断线重连 | 断线 60s 内可恢复、超时托管 | 0.5 天 |
| 房间详情分享 | 邀请链接 / 房间号复制 | 0.2 天 |

合计 **3-4 天**（Node.js 方案，规则代码直接复用）。

## 四、ET 是否合适

### ET 是什么

[egametang/ET](https://github.com/egametang/ET) 是 C# 的**分布式游戏服务器框架**：Entity-Component 架构 + Actor 模型 + 协程，自带网络层（TCP/KCP/WebSocket）、协议代码生成、热重载、压测工具。国内 MMO、棋牌、SLG 用得较多。

### 对本项目的真实收益

| 收益 | 说明 |
|---|---|
| 复用 C# 规则引擎 | `/workspace/guandan-game/server/Guandan.Core` 已有 C# 版引擎（39/39 测试通过），可直接搬进 ET 的 Scene |
| 房间/匹配设施齐全 | Scene/Actor 天然隔离，分区分服、跨服、匹配都是现成的 |
| 长期可扩展 | 后续要做多玩法平台、赛事、排行榜，ET 的骨架够用 |

### 真实成本（重点）

| 成本项 | 说明 |
|---|---|
| **跨语言协议** | ET 默认 MemoryPack（C# 专属）。JS 客户端要么改用 Protobuf（需改 ET 序列化配置），要么自己实现 MemoryPack 解码；ET 的 RPC 封装（Session / MessageObject / 消息头）也要在 JS 里复刻一遍 —— **这是最容易踩坑、最容易拖工期的地方** |
| 部署依赖 | 需要 .NET 8 运行时 + MongoDB（+ Redis）。当前服务器 **2 核 3.7G，MongoDB 常驻就吃掉 300-500MB**，跑得动但不宽裕 |
| 学习曲线 | Entity/Component/Actor/Coroutine 一套自洽体系，文档偏少、版本迭代快，排错要读源码 |
| 与现有前端脱节 | 前端是 JS，规则引擎也是 JS；上 ET 等于把 `Rule` 用 C# 再实现一遍（已有，但要保证两边行为完全一致，要跑对拍测试） |

### 结论

> **ET 不是「更高级所以更好」，而是「更重、更适合平台化」**。
> 一个 4 人房间的掼蛋，ET 的能力 90% 用不上，但你得为它付出协议跨语言 + 部署 + 学习三份成本。

**判断标准很简单**：

- 只想让朋友扫码/点链接进来打牌 → **Node.js 方案**，3 天做完
- 要把掼蛋做成商业化平台（多玩法、分服、赛事、数据后台、长期运营）→ **ET**，值得投入 1-2 周打地基

## 五、推荐路线

### 阶段 1：房间号联机（Node.js，3-4 天）

- 服务端：`Node 18 + ws`，直接 `import` 现有 `engine/`（零改动）
- 协议：JSON over WebSocket（先不做二进制压缩，足够）
- 房间：6 位数字房间号，`ws://host/guandan/ws?room=123456&seat=2`
- 客户端：`GameScene` 增加「联机模式」——牌局状态由服务端推送，客户端禁止本地改状态
- 部署：与现有前端同机，PM2 + Nginx `location /guandan/ws` 反代（WebSocket upgrade）

### 阶段 2：微信生态（依赖域名备案）

1. 准备**已备案域名** + Let's Encrypt 证书，替换现在的 IP + 自签
2. 分享链接带房间号参数，微信内直接可打开
3. 若要分享卡片：申请服务号 → 配置 JS 安全域名 → 后端提供签名接口 → 前端 `wx.updateAppMessageShareData`

### 阶段 3（可选）：ET 平台化

如果阶段 1 验证了需求，再把服务端迁到 ET，复用 `Guandan.Core`，获得分区分服、热更新、运营后台能力。
**此时前端协议层已经抽象好，迁移成本可控。**

## 七、已实现（本次交付）

### 服务端 `server/`

| 文件 | 作用 |
|---|---|
| `index.js` | HTTP 健康检查 + WebSocket 服务（`/ws`），房间路由、心跳、空闲回收 |
| `room.js` | 房间：座位管理、权威牌局、机器人补位、断线托管、结算广播 |
| `game/engine/` | 复制自 `src/game/engine`（纯 JS 规则引擎，零改动复用） |

**已实现能力**

- 6 位房间号：**创建房间**生成新号，**输入房号**进房；房号不存在会明确提示，不再"顺手建房"
- 房间**默认空位，不自动补机器人**；4 个真人坐满才自动开局
- 房主（第一个进房的人）可在房间内「添加电脑 / 移除电脑 / 开始游戏」，房主离开自动移交
- 服务端权威洗牌发牌、出牌校验（客户端无法作弊）
- 单回合 30 秒限时，超时自动按 AI 出最小可压牌 / 过牌
- 断线保留座位 60 秒，重连自动恢复；局中离线立即机器人托管
- 一局结束只清理掉线真人、保留房主添加的电脑，6 秒后自动开下一局
- 等级按队累计（服务端权威），进贡/还贡/抗贡全自动

**房间状态机**

```
waiting ──(房主点"开始游戏" 且 4 座位齐 / 4 个真人坐满)──▶ playing
   ▲                                                        │
   └──────────(结算后有人走了、座位不齐)────────────────────┘
                            settled ◀── 一方出完 ── playing
```

**协议**（JSON over WebSocket）

```
C→S  {t:'join', room, name, create}  {t:'start'}  {t:'addBot'}  {t:'removeBot', seat}
     {t:'play', cards:[...]}  {t:'pass'}  {t:'leave'}  {t:'ping'}
S→C  {t:'joined', seat, room}  {t:'sync', ...全量状态}  {t:'settle', ...}  {t:'error', msg}
```

`sync` 是**全量状态 + 每人私有手牌**：客户端收到即重绘，不需要增量逻辑。
`seats[]` 里带 `host / bot / online / empty`，客户端据此区分「房主 / 电脑 / 离线 / 空位」。

**视角换算**：自己永远渲染在 0 号位，其余按相对座位映射；等级按「我队/对方队」换算，保证任意座位进房画面一致。

**手牌点选**：牌的间距 42px、牌宽 142px，互相重叠时 Phaser 逐张 hitTest 只会命中深度最高的那张，
所以改成「手牌带状区域按 x 反算索引」，并支持 pointerdown 后拖动连续划选（按下时定选/反选方向）。
